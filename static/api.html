▦ Block ArchiveAPI v1

CONNECT BY BLOCK CODE

A stable link to every block.

Use the generic API to retrieve images and archive history or connect a block to a record in another system. All block, image and event endpoints require authentication.

Authentication

Local API clients send Authorization: Bearer <token>. The server generates the token in .localdata/api-token, or in your configured data directory. Keep it private. The browser uses a separate HttpOnly session cookie; it does not receive the API token.

curl --get 'http://127.0.0.1:8780/api/v1/blocks/by-code' \
  --header "Authorization: Bearer $BLOCK_ARCHIVE_TOKEN" \
  --data-urlencode 'block_code=TEST-2026-001234-B4'

Archive identity

A record contains a full block_code and the structured fields archive_year, case_number, subspecimen, and cassette_number. B4 means subspecimen B, cassette 4. The description records the known cassette contents. Each record has an immutable UUID for API operations.

Block codes are matched exactly after trimming and ignoring case. The year–case–subspecimen–cassette combination must also be unique. Case numbers retain their leading zeroes but are sorted numerically. This installation represents one archive; identical codes across different laboratories need separate namespaces or installations.

Record changes safely

Every change to an existing block must include actor and the record’s current expected_version. Use the version returned by each successful request for the next step. A stale version, duplicate block or invalid movement returns HTTP 409. Refresh the record and review the change before retrying.

POST /api/v1/blocks/{id}/rearchive
{
  "actor": "TEST-TECH",
  "expected_version": 8,
  "photo_id": "<UUID from a new photo in this cycle>",
  "note": "Returned to the filing sequence"
}

Initial filing requires a baseline photo. After checkout and completion of cutting, rearchiving requires a post_cut photo uploaded in that cycle. Uploading identical bytes from an earlier image is rejected. This verifies a new upload, not the physical capture date; the technician must take and check the photograph.

Upload a photograph

curl 'http://127.0.0.1:8780/api/v1/blocks/BLOCK_UUID/photos' \
  --header "Authorization: Bearer $BLOCK_ARCHIVE_TOKEN" \
  --form 'actor=TEST-TECH' \
  --form 'expected_version=7' \
  --form 'kind=post_cut' \
  --form 'file=@new-photo.jpg'

Use single-frame JPEG, PNG or WebP, up to 20 MB and 40 megapixels. Responses include original and thumbnail URLs relative to this server. Send authentication when retrieving those URLs. Images are linked to the selected block; the service does not perform OCR or verify printed labels.

Link and synchronize other data

Save an external reference with a system, external_id and optional HTTPS/HTTP url. These references are searchable. The API stores the reference without contacting that system.

Poll /api/v1/events?after=CURSOR&limit=100. Process events in sequence, then persist next_cursor. Continue while has_more is true. Store processed sequence numbers to make your consumer idempotent. This release does not send webhooks.

Deployment boundary

This version runs on loopback for one local archive. The shared API token is not individual staff authentication; the recorded operator is self-declared. An institutional deployment needs identity integration, role permissions, HTTPS, approved storage and retention, and review of audit requirements. Source photographs and backups may contain identifiers and original metadata.
